# Behemoth — 체감 개선과 확장 실행안

작성: 2026-10-28. 사용자 피드백을 정리한 제안이며 구현 완료 목록이 아니다.
현재 코드와 데이터 구조만 확인했다. 거미·해골의 전투 상황, 화면의 먹선과 UI 문제는 사용자 관찰을 출발점으로 삼았으며 이번 정리에서 런타임 재현하지 않았다.

**후속 지시 반영:** 첫 실행 범위는 거미·해골의 개별 학습 개선에서 **1막 전체의 어려움·체력·피로도 관리**로 확장되었다. 초반 이벤트 배치, 지도 조작성, 베기·준비/공격 모션, A–B 수준의 자연스럽고 패턴이 읽히는 기술명도 함께 작업한다. 현행 요구·적용 이력·검증은 [1막 제작 기록](../Production/ActOneExperience-2026-10-28/Direction.md)을 우선한다. 아래 첫 실행 제안은 초안의 기록이다.

## 목표와 순서

먼저 **첫 전투에서 행동을 읽고 대응하는 재미**, 다음으로 **1막을 탐험하고 빌드를 선택하는 재미**, 마지막으로 **다시 시작할 때 방향을 정하는 재미**를 만든다.

| 순서 | 작업 묶음 | 먼저 하는 이유 | 다음 단계로 넘어갈 기준 |
| --- | --- | --- | --- |
| 1 | 첫 전투의 학습·손맛 + 대표 화면의 시각 기준 | 적이 행동하기 전에 죽으면 모션·약점·가드가 제 역할을 못 한다. 시각 기준 없이 전체 그림을 교체하면 재작업이 커진다. | 대표 적의 예고→대응→약점 파괴→후속 공격을 경험하고 구분할 수 있다. |
| 2 | 주문 입력 소규모 프로토타입 | 드로잉의 재미·피로도는 설계 문서만으로 결정할 수 없다. HUD와 주문 체계를 크게 바꾸기 전에 확인한다. | 의도한 주문을 빠르게 쓰고, 취소·오인식·대상 선택을 납득할 수 있다. |
| 3 | 1막 동선·지도·이벤트 경험 | 전투 학습 이후에 휴식과 선택이 등장해야 자원과 보상의 의미가 생긴다. | 초반 전투 경험, 야영지 거리, 길 선택, 이벤트 선택지가 자연스럽게 이어진다. |
| 4 | 확정된 규칙에 맞춘 HUD·아트 전체 적용 | 앞 단계에서 정한 화면 크기·입력·이벤트 구성을 공통 규칙으로 적용한다. | 실제 표시 크기에서 읽히고 배경·캐릭터·아이콘·UI의 표현이 어울린다. |
| 5 | 전직 소규모 프로토타입 | 기본 전투와 1막이 안정돼야 전직의 선택 시점과 체감 효과를 판단할 수 있다. | 같은 캐릭터의 두 전직이 플레이 판단을 다르게 만든다. |
| 6 | 기억·퀘스트·해금 | 성장 보정이 기본 전투의 문제를 가리지 않도록 뒤에 붙인다. | 처음부터 플레이가 성립하며 반복 플레이에서 시작 빌드의 선택지가 넓어진다. |

순서 4의 모든 UI를 기다리는 것은 아니다. 자원 HUD, 최소 주문 HUD, 이벤트 선택지 UI는 해당 기능을 검증하는 첫 버전에 함께 넣는다. 전체 아이콘·일러스트 제작만 시각 기준 확정 뒤에 진행한다.

## 1. 첫 전투와 시각 기준

- [ ] 거미: 시작하자마자 평타만으로 첫 행동 전에 죽는 상황을 재현하고, 첫 예고와 대응 기회를 확보한다.
- [ ] 해골: 첫 약점 파괴가 곧 처치로 끝나는 상황을 재현하고, 기절한 적에게 후속 공격하는 흐름을 경험하게 한다.
- [ ] 몬스터 idle→준비→공격의 실루엣·무게중심·무기 위치를 과감하게 구분한다.
- [ ] 캐릭터 idle→입력 유지 중 준비→놓는 순간 공격의 흐름을 만든다. 기존 공격·가드 조작과 충돌하는지 확인한다.
- [ ] 베기 이펙트에 방향·궤적·타격 순간을 담는다. 빗나감과 명중을 구분하고 약점과 공격 예고를 가리지 않는다.
- [ ] 대표 배경 하나와 캐릭터·거미·해골로 먹선 기준 화면을 만든다.

먹선 문제는 원본 이미지 해상도만 올려서는 해결되지 않을 수 있다. **최종 화면에 표시되는 크기에서 선이 차지하는 두께**를 기준으로 외곽선·내부선·먹의 농도·질감을 맞춘다. 축소 필터와 현재 렌더링 경로도 확인한다. 외곽선만 덧대는 방식은 내부 묘사의 가는 선을 해결하지 못하므로 대표 화면으로 비교한 뒤 원화 수정 범위를 결정한다.

밸런스는 체력 일괄 상향으로 시작하지 않는다. 현재 Warrior와 B1/B2/B3의 디자이너 조정을 기준으로 보존하고, 문제를 재현한 적의 체력·약점 내구도·행동 시점·브레이크 후 생존 시간을 구분해 조정한다. 일부러 기다리게 하거나 강제 무적으로 패턴을 보여주는 방식은 우선안에서 제외한다. 강해진 빌드가 약한 적을 빠르게 처치하는 경우까지 막을 필요는 없다.

## 2. 주문 입력: 먼저 세 가지를 비교

### A안 — E를 누르고 자유 드로잉 (우선 추천)

E 누름→입력 흔적 표시→별·삼각형·소용돌이·번개 중 하나를 그림→현재 인식 후보와 대상 미리 표시→E를 놓으면 자동 대상 지정 후 발동.

- 장점: 주문을 직접 그리는 정체성이 강하다.
- 검증할 점: 전투 중 그리는 시간, 반복 피로, 오인식, 마우스 이동 거리.
- 기본 피드백: 궤적, 인식한 문양·주문명, 대상 강조, 마나 부족·재사용 대기 표시.
- 인식 불확실·빈 궤적·취소는 발동하지 않고 자원을 소비하지 않는다. 취소 입력도 제공한다.
- 인식 실패와 실제 시전 중단을 구분한다. 자원 차감 시점과 기존 시전 시간의 관계를 명시해 이중으로 기다리는 느낌을 피한다.
- 프로토타입에서 실시간과 약한 감속을 비교한다. 감속은 반복 눌러 상시 방어 수단으로 쓰이는지도 확인한다.

### B안 — 희미한 문양을 따라 그리기

입력 중 작은 가이드와 시작점을 제공하고 느슨한 오차를 허용한다. 자유 드로잉보다 학습과 인식이 쉽다. 대신 전투를 보면서 가이드를 따라가는 시선 부담을 확인해야 한다. A안의 학습 보조나 접근성 옵션으로도 적합하다.

### C안 — 짧은 기호로 축약

복잡한 별·소용돌이를 짧은 꺾은선 등으로 축약해 선택하고, 발동 순간 완성된 마법진을 보여준다. 사용 속도와 반복 피로에 유리하다. 직접 그리는 체감이 충분한지 A안과 비교한다.

### 주문 규칙과 HUD

- [ ] 동시 소지는 최대 4개. 방향별 슬롯·배치 의존과 미소지 주문을 별도 책에 쌓아 다시 장착하는 흐름을 새 규칙에 맞춰 정리한다.
- [ ] 새 주문 획득 시 빈 자리에 추가하거나, 가득 찼으면 기존 주문 교체/새 주문 버리기를 제공한다. 중복 획득에도 별도 중첩 없이 버리기/교체 규칙을 일관되게 적용한다.
- [ ] 45도 회전한 정사각형 프레임을 사용하고 내부 그림·숫자는 정방향을 유지한다. 문양, 비용, 재사용 대기를 읽을 수 있게 한다.
- [ ] 위자드는 파이어볼트를 시작 주문으로 가진다. 클래스 조건 분기 대신 시작 주문 데이터로 설정한다.

**결정해야 할 설계 문제:** 문양이 네 종류이고 주문은 그보다 많을 때, 같은 문양의 서로 다른 주문을 함께 소지할 수 있어야 한다.

프로토타입 추천은 소지 주문에 서로 다른 네 문양을 연결하는 방식이다. 획득 시 빈 문양을 배정하고 소지 중에는 바꾸지 않으며, 교체 시 기존 문양을 이어받는다. HUD 위치는 시전 조건에 쓰지 않는다. 단, 같은 주문의 문양이 런마다 바뀌는 학습 비용이 있으므로 문양을 주문의 고유 정체성으로 삼고 싶다면 문양 종류를 늘리는 안을 비교한다. 이는 확정 요구사항이 아닌 검증할 제안이다.

자동 타기팅은 모든 주문에 동일한 최단거리 규칙을 적용하지 않는다. 단일 공격·범위·연쇄별로 재사용 가능한 대상 선택 규칙을 데이터에 둔다. 입력 중 표시한 대상과 실제 발동 대상을 일치시키고, 대상 사망이나 유효 대상 없음도 처리한다.

## 3. 1막·지도·이벤트

### 동선

- [ ] 여신상·우물·상점보다 앞에 기본 전투를 충분히 경험하는 구간을 둔다. 첫 시안은 2~3전으로 시작하되 고정 사양이 아닌 조정값으로 둔다.
- [ ] 야영지에 시작점 기준 최소 경로 거리를 적용한다. 화면상 거리 대신 실제 이동 간선 수를 기준으로 한다.
- [ ] 이벤트·회복·상점의 등장 조건은 거리와 실제 전투 경험을 구분한다. 우회로로 초반 학습이 빠지거나 모든 보상이 늦어지지 않는지 확인한다.
- [ ] 연속 분기와 불필요한 순환을 줄인다. 보상과 위험이 다른 갈림길은 남기고, 분기 직후 다시 합류하는 혼란을 줄인다.
- [ ] 지도를 연 상태에서 현재 위치·이동 가능한 연결·선택 결과를 확인하고 길을 선택할 수 있게 한다.
- [ ] 지도와 보유품 메뉴의 간격을 줄인다. 지도 위 UI가 길 선택을 가리지 않게 한다.

### 이벤트

- [ ] 이상한 이벤트를 먼저 선별한다. 삭제보다 랜덤 풀 제외를 활용해 기존 제작 내용을 보존한다.
- [ ] 선별 기준: 선택의 이유가 생기는가, 비용·위험을 이해할 수 있는가, 현재 진행도에 맞는가, 결과가 설정과 맞는가, 다른 선택지가 실질적으로 의미 있는가.
- [ ] 선택지 페이지 넘김을 없애고 해당 결정에서 고를 수 있는 선택지를 한 화면에 모은다. 읽기 어려울 정도로 글자를 줄이지 않도록 선택지 문장과 구성도 편집한다.
- [ ] 조건 미충족 선택지에는 이유를 표시하고, 선택 뒤 실제 결과와 획득·소모를 명확히 보여준다.
- [ ] 채택된 이벤트별로 전용 일러스트를 제작한다. 같은 상황의 장면 분기는 필요에 따라 공유한다.

선택지 페이지 제거와 이야기의 결과 분기 제거는 구분한다. 이야기의 단계별 결과·조건 분기는 유지하면서 현재 고를 선택지를 숨기는 페이지 이동을 제거하는 방향을 제안한다. 이벤트 전체를 단일 장면으로 합치는 작업은 별도 설계 판단이다.

공급된 Slay the Spire 이벤트 참고의 선택 경험을 유지하고 데이터의 출처·참고 의도에 기록한다. 서로 다른 결과를 모두 같은 후불 패널티 구매로 통일하지 않는다. 일러스트는 선별과 텍스트 개편 뒤에 제작한다.

## 4. HUD와 아트 적용

- [ ] 체력은 초상화에 붙여 런 전체 자원으로 지속 표시한다.
- [ ] 포션 인벤토리는 초상화 아래에 배치한다. 사용 가능 여부·수량·사용 결과를 표시한다.
- [ ] 가드와 마나는 같은 시각 규칙의 전투 자원 묶음으로 만든다. 전투 진입 시 준비 상태, 소모·회복, 전투 종료 시 처리를 알려준다. 실제 초기화 규칙도 함께 확인한다.
- [ ] 체력과 전투 자원은 프레임·색·간격 규칙을 공유하되, 관리 주기가 구별되도록 배치한다.
- [ ] 상단 유물·포션 나열을 재편한다. 포션을 초상화 아래로 옮긴 뒤 상단은 유물 중심으로 정돈한다. 과다 보유·툴팁·추가 획득 시 레이아웃도 확인한다.
- [ ] Perk·유물·포션 아이콘을 현재 2D 먹선 화풍에 맞춘다. 실제 HUD 크기의 표본을 먼저 확정하고 전체를 교체한다.
- [ ] 대표 화면의 먹선·모션 기준을 나머지 몬스터와 캐릭터에 확장한다.

모든 UI 문구는 TextMeshPro와 한국어 텍스트 키/CSV 흐름을 유지한다. 씬·프리팹·데이터를 에디터에서 확인할 수 있게 저장하고 수동 베이크 메뉴를 필수 단계로 만들지 않는다.

## 5. 전직 프로토타입

- [ ] 한 캐릭터, 두 전직, 런 중 한 번의 선택으로 시작한다.
- [ ] 첫 시안은 1막 중반에 두어 선택 전후의 전투를 모두 경험하게 한다. 보스 직전·보스 뒤는 이후 비교 후보로 둔다.
- [ ] 예시: 가드 성공 후 반격을 강화하는 수호 방향 / 약점 파괴 후 연속 공격을 강화하는 돌파 방향.
- [ ] 선택 화면에서 바뀌는 행동과 현재 빌드의 연결을 설명하고, 다음 전투에서 효과를 명확히 알린다.

전직은 단순 공격력 배수만 다르게 만들지 않는다. 같은 적을 상대할 때 기다리는 시점·자원 사용·공격 순서가 달라지는지 본다. 영구 단순 능력치는 PerkData, 발동·조건부 효과는 재사용 가능한 EquipmentAbility와 관련 데이터로 표현한다. 캐릭터 이름·아이템 ID별 일회성 분기를 추가하지 않는다.

## 6. 기억·퀘스트·해금

기억은 **원래 지녔던 능력을 잊었다가 되찾는 것**이며, 반복 플레이에서 시작 빌드의 방향을 정하는 시스템으로 묶는다.

- [ ] 퀘스트로 캐릭터·Perk·유물 선택지를 해금한다. 잠긴 항목의 조건과 달성 진행도·해금 결과를 보여준다.
- [ ] 해금된 콘텐츠가 어디에 쓰이는지 구분한다: 캐릭터 선택 / 런 중 보상 후보 / 출발 전 기억 선택.
- [ ] 기억에서 출신·시작 특성 또는 유물을 선택한다. 출신은 클래스와 독립이므로 군인·귀족·죄수 출신 Warrior 등이 가능하다.
- [ ] 군인은 전투, 귀족은 이벤트 선택, 죄수는 위험과 대가를 활용하는 방향의 후보로 둔다. 출신 효과는 재사용 가능한 조건·효과 데이터로 만든다.
- [ ] 시작 Perk 하나를 선택하는 안을 검증한다. 레벨업으로 얻던 능력을 기억해 내는 설정으로 연결한다.
- [ ] 영구 저장·재시작 복원·조건 중복 달성·중복 보상 방지·새 런에만 시작 혜택 적용을 처리한다.

첫 MVP는 퀘스트 소수와 **기억 선택 한 칸**으로 제한한다. 시작 Perk 1개를 먼저 검증한 뒤 출신·시작 유물로 확장한다. 이는 최종 범위를 줄이는 것이 아니라 효과를 분리해서 평가하기 위한 단계다. 클래스 고유 시작 유물과 기억의 선택 유물을 어떻게 함께 적용할지도 명시한다.

누적 공격력 상향보다 시작 방향의 선택 폭을 우선한다. 전투와 이벤트 양쪽에서 통하는 퀘스트를 구성하고, 특정 정답 행동을 반복시키는 과제가 되지 않게 한다. 새로운 항목 해금으로 보상 풀이 넓어지는 것이 기존 빌드에 불리하게 작동하는지도 확인한다.

## 첫 실행 묶음과 검증

**첫 실행은 거미·해골의 전투 흐름, 플레이어 준비 모션, 베기 피드백, 대표 화면의 먹선·자원 HUD까지**로 제한하는 것을 추천한다. 이후 주문 네 문양을 작은 테스트에서 비교하고 채택안을 정한다. 바로 모든 몬스터·이벤트 그림을 다시 만들거나 전직·영구 성장을 동시에 넣지 않는다.

| 변경 묶음 | 필요한 해당 범위 라이브 검증 | 남겨야 할 기록 |
| --- | --- | --- |
| 전투 | 시작 기본 상태의 거미·해골, 예고·약점 파괴·기절 후 공격, 입력 유지·해제·취소, 베기 명중·빗나감 | 행동 기회, 처치 시점, 상태 구분이 되는지 |
| 먹선·HUD | 실제 게임 표시 크기, 자원 소모·회복, 포션 사용, 과다 보유, 툴팁 | 전후 화면, 가독성·겹침 |
| 주문 | 네 문양 각각, 다양한 크기·속도·시작 위치, 모호한 입력·취소, 마나 부족·쿨다운·대상 없음·대상 사망, 연속 사용 | 의도한 주문/인식 결과, 입력 시간, 오발동·실패·피로 |
| 소지 주문 | 0~4개, 다섯 번째 획득, 동일 주문·문양 충돌, 교체·버리기 | 소지 한도, 바인딩 일관성, 안내 |
| 동선·지도 | 재현 가능한 여러 시드의 시작 경로·캠프·분기, 지도 열린 채 경로 선택 | 시작 거리와 실제 전투 수, 선택 방해 여부 |
| 이벤트 | 채택 이벤트의 모든 선택지와 조건 충족/미충족·결과 | 한 화면 가독성, 설명과 실제 결과의 일치 |
| 전직 | 같은 진행도에서 전직 전후의 직접 영향 범위 | 판단·행동 변화, 선택 시점과 효과 체감 |
| 기억·퀘스트 | 달성→해금→선택→새 런→종료 후 재실행, 중복 달성 | 저장·보상·시작 적용 결과 |

이번 문서는 계획 정리이므로 위 검증은 모두 미실행이다. 구현 시 변경한 상호작용을 사용자 Unity Editor에서 확인하고 기록한다. 전체 클래스 DPS 비교·전체 시스템 회귀·무거운 백그라운드 검증은 자동 실행하지 않으며 별도 요청 시 한 번에 한 스위트만 진행한다.

## 현재 구현에서 확인한 접점

- `Assets/Scripts/Data/PlayerCombatData.cs`: `startingSpells`로 시작 주문 지정 가능.
- `Assets/Scripts/Data/SpellData.cs`, `Scripts/Run/RunExpansion.cs`, `Scripts/UI/SpellbookView.cs`: 현재 방향 슬롯과 주문 소지·장착 흐름이 연결되어 있음. 드로잉 변경은 입력만 교체하는 작업이 아님.
- `Assets/Scripts/Data/RandomEventData.cs`: 일러스트, 조건, 장면 분기, 랜덤 풀 제외, 참고 출처 필드가 있음.
- `Assets/Scripts/UI/RunExpansionView.cs`: 선택지 목록의 페이지 처리. `EventSequencePresentation.cs`의 이야기 장면 이동과 별개임.
- `Assets/Scripts/Dungeon/Generation/DungeonGenerator.cs`: 보스·일부 상자는 거리 제약을 쓰지만 야영지는 일반 무작위 배치 경로를 사용함.
- `Assets/Scripts/UI/RunHudView.cs`: 체력·초상화·Perk·유물·포션 표시 기반이 있음.

이 접점은 확장 위치에 대한 확인이다. 기능이 현재 런타임에서 정상 동작한다는 검증을 뜻하지 않는다. 기존 작업 파일은 수정하지 않았다.
